# 接口先行的并行开发

当多个任务共用正在变化的边界时，本指南用于判断任务是否可以开工以及如何集成。[开发流程](development-process.zh.md)仍负责代理委派、评审、提交和必需门禁。[English](interface-first-parallel-development.md)。

## 判断是否需要独立的契约落地任务

分配工作前，先画出提供者 → 消费者的依赖边。在活跃 OpenSpec 的 `design.md` 和任务依赖图中记录每个边界的判断。

| 边界 | 计划方式 |
| --- | --- |
| 行为已有测试固定的稳定接口 | 任务使用当前版本和聚焦测试；无需新建契约落地任务。 |
| 至少两个可独立验收的任务共用新接口或实质变化的接口 | 先由控制者完成一个可编译的契约落地任务，再启动这些任务。 |
| 仅一个实现任务使用的私有接口 | 接口和实现留在同一任务。 |
| 共用的可变文件、注册表、模式版本、适配器或迁移 | 指定独占的串行集成负责人，即使其他任务共用同一契约。 |

接口可以是函数签名、语义值、Rust trait、Go interface、模式、消息或夹具格式。只有消费者确实需要替换实现时，才引入 trait 或 interface；不要仅因并行开发而增加抽象。契约放在所有消费者都能无环依赖的最底层稳定所有者处，只公开最小语义表面；存储布局、解析器状态、算法和提供者辅助函数保持私有。如果没有符合条件的共享边界，计划应记录无需单独落地的理由。

## 派发前冻结的契约说明

控制者在活跃 change 的 `design.md` 或链接的任务说明中，为每个共享边界填写一份契约说明。`tasks.md` 仍是唯一的任务状态来源。规划时先指定契约落地的前置任务；该任务通过后填入已验收 SHA。达到可派发状态时，下表每一项都须有具体值，或明确说明不适用。

| 字段 | 必须确定的内容 |
| --- | --- |
| 身份与所有权 | 契约名、所属模块/文件、基线来源和已验收契约的提交 SHA；准确的提供者与消费者任务。 |
| API | 精确的操作签名与字段类型、既有类型和新类型的所有者、允许的依赖方向、版本或兼容性身份。 |
| 数据语义 | 单位、坐标、顺序、默认值和未知值、合法与非法范围、归一化、可变性、所有权和生命周期。 |
| 调用生命周期 | 状态转换、并发与取消、临时空间的所有权和复用、结果发布的原子性、错误优先级和容量单位。 |
| 上限 | 最大数量、字节数、工作量和分配量；溢出行为与热路径限制。 |
| 示例 | 结果精确的成功、非法输入、边界和失败案例；兼容性相关时指定独立预期来源。 |
| 文件与门禁 | 契约、提供者、消费者和集成负责的路径；测试发现和运行命令；回滚单元与下游门禁。 |

不能用“由实现决定”“处理边界情况”或让 worker 自行选择来掩盖设计缺口。worker 可以选择私有辅助函数名和等价的局部代码组织，但不能重新定义公开行为或所有权。

## 一次性交付可编译契约

1. 创建能编译的最小声明，以及构造真实夹具所需的验证构造器或解析器。如果模块注册需要未来的提供者文件，可预建可编译的空文件并保留给对应负责人。不能加入返回伪造成功、以占位方式 panic，或悄悄退回其他所有者的生产操作。
2. 用确定性的替身让消费者仅依赖公开表面编译，并实际执行至少一条成功路径和一条带类型的失败路径。适用时检查真实构造器验证、顺序和容量案例。只编译类型不能证明行为。
3. 评审并验证契约落地，在 `ledger.md` 记录提交 SHA 和准确命令。每个独立的提供者或消费者任务都写明该 SHA 和直接前置任务。只有契约身份验收后，相关工作才能开始。

契约落地证明各方可在不阅读彼此内部实现的条件下开发；它不证明具体提供者或集成后的运行时正确。

## 按依赖与所有权安排并行

```text
已验收契约 SHA
  ├─ 提供者 A ─┐
  ├─ 提供者 B ─┼─ 串行共用适配器/注册表 ─ 集成门禁
  └─ 消费者 C ─┘
```

两个节点只有在全部前置证据已验收、可编辑文件不重叠、不互相修改对方拥有的共享状态、也不依赖未裁定的版本或兼容性问题时，才可同时开工。每个节点要有精确的可编辑和只读文件，以及可独立评审的测试周期。独立 worktree 或独占文件集可以从同一个已验收 SHA 开始。共用适配器、生成产物、注册表、迁移和版本升级必须有唯一编辑者或明确的串行顺序。逐个集成已评审结果，并在合并 SHA 上重跑受影响的下游检查。任务可并行不改变项目的代理并发与委派政策。

## 区分三层证据

| 门禁 | 必须实际执行 | 不能证明 |
| --- | --- | --- |
| 契约 | 公开调用、经验证的夹具、消费者替身的成功和失败路径。 | 真实提供者正确。 |
| 提供者 | 真实实现的准确成功、错误、上限与顺序案例，以及聚焦回归或独立预期来源。 | 真实消费者集成。 |
| 集成 | 在同一记录 SHA 上运行真实提供者和消费者，并执行适用的 ABI、协议、存档、语料或独立预期检查。 | 已执行案例集合以外的行为。 |

清单名称、未执行的测试、类型编译或替身通过，都不能关闭提供者或集成任务。在 change 的 ledger 中记录非零发现和执行案例数、命令、结果、SHA 及适用的夹具身份。只有指定门禁通过后才能在 `tasks.md` 勾选任务。

## 有控制地修改冻结契约

实现中发现冲突时，worker 报告已核实的来源、失败案例、确切冲突字段或操作，以及受影响任务。控制者裁定契约，更新活跃设计、必要的行为 delta spec、所有受影响任务说明和契约测试，再落地新的已验收 SHA。受影响任务变基或以其他方式采用新身份，并重跑门禁。未使用变化表面的任务可以继续。线协议、存档和 ABI 变更仍遵循既有兼容性与独占规则。worker 不得为通过本地测试而悄悄修改共享声明。

## 规划示例：Rust 数值闭环

活跃的[数值闭环设计](../openspec/changes/rust-native-numerical-closure/design.md)规划将节点 1.2 用作类型化 `mornlea_engine::native::contracts` 契约落地，其中包含经过验证的共享输入和操作 trait 的测试替身。取得**已验收的实现 SHA**之后，文件互不重叠的碰撞、射线、世界、流体、网格和寻路提供者节点才可基于该契约开工。`ffi.rs` 适配和语料注册有串行负责人，之后执行真实 ABI 与来源绑定的语料测试。撰写本指南时，契约落地与提供者仍然**只有规划，尚未实现**；OpenSpec 状态本身不是验收证据。这个示例展示任务依赖关系，不宣称所有开发线已经通过。
