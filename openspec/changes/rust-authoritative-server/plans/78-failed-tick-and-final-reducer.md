## Shared reducer algorithm and unwind ownership

Private reduce_tick_inner(state,budget,publish:bool)->Result<TickPublication,ServerError> contains the existing wrapper chain. A private validated mode entry wraps the complete inner call with catch_unwind(AssertUnwindSafe); returned error calls fail_tick with the exact error, panic maps Internal{invariant:"authoritative tick panic"} and calls fail_tick. This catches trusted provider unwinds without claiming native UB/abort recovery.

Within inner, drain mailbox/companion/login exactly as before; move fluid/farmland schedules out exactly as before; construct exclusive TickContext. A second catch_unwind closure borrows that context and both schedules. Inside it: stage logins, freeze environment, feed companion actions, dispatch_rows(...)?, build the same overlays/events/counters, then commit_carried ONLY after dispatch succeeds. Return the owned output tuple. After closure result, always drop context first (its existing Drop returns partial resident owners/dirty set), then restore BOTH moved schedules to authority, then propagate closure error/panic. No earlier accepted actor/block write is undone or finalized on dispatch failure. Event/viewer overlays remain ephemeral as currently; original receipt/watermark treatment is preserved and no selected command is requeued.

Only on success retain Active viewers/commit_viewers/project final player updates/build the same publication. If publish==true, publication::publish_tick(state,publication.clone())?; otherwise skip this call entirely. Return Ok(publication). Outer catch handles a later commit/projection/delivery unwind; schedules have already returned on all context-stage failures and returned errors. Update misleading source comments asserting errors never stop the tick. No added production fault hook.
