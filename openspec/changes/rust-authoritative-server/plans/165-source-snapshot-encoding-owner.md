## Exact APIs and record semantics

Export core::source_encoding. Public non-Clone SourceSnapshotEncoding has private pool:ChunkEncodingPool, requests:Vec<SourceEncodeRequest>, stopping:bool, closed:bool. Private record has session:SessionKey, request:ChunkEncodeRequestId, capture:ChunkSaveView. Vec admission is capped by the actual pool's MAX_CHUNK_ENCODE_REQUESTS8, including cancelled started requests that the book no longer routes. Public try_new(workers:usize)->Result<Self,ServerError> constructs the actual pool OFF TICK; workers0/3 refuse chunk_encode_workers and1/2 use real owners. No pool replacement or mutable pool getter.

Public methods:

- request(&mut self,session:SessionKey,capture:ChunkSaveView)->Result<ChunkEncodeRequestId,ServerError>.
- contains(&self,session:SessionKey,key:ChunkKey)->bool.
- retained_requests(&self)->usize (routing records), charged_requests(&self)->usize (actual pool owned_jobs; includes cancelled started/held results).
- retain_current(&mut self,is_current:impl FnMut(SessionKey,ChunkKey,u64,u64)->bool)->Result<usize,ServerError>; predicate arguments are exact session, capture key, capture generation, capture revision. Caller supplies nonblocking scalar eligibility, not a fresh capture token.
- collect_ready(&mut self)->Vec<SourceEncodeResult>.

Public non-Clone SourceEncodeResult has private original session/request/capture and result:Result<EncodedChunkSnapshot,ServerError>, getters session()->SessionKey, request()->ChunkEncodeRequestId, capture()->&ChunkSaveView, result()->&Result<EncodedChunkSnapshot,ServerError>, into_parts(self)->(SessionKey,ChunkEncodeRequestId,ChunkSaveView,Result<EncodedChunkSnapshot,ServerError>). Success retains the exact original Arc token; failure retains the same request/session/capture and actual error. No fabricated Ready, publication receipt, new ACK or successful wire outcome.

request precedence: closed=>InvalidState Closed, stopping=>Closing, zero generation/revision=>InvalidInput chunk_network_snapshot, existing same(session,key)=>InvalidInput source_chunk_encode, then existing actual pool admission/capacity/monotonic-ID errors. A changed generation/revision capture cannot silently replace the same pending key: caller must explicitly cancel obsolete work first. Equal numeric capture tuple cannot replace original token. Clone only the capture Arc for the routing record; move supplied capture into start_encode, append record only on actual successful admission. IDs remain independent and monotonic; rejected duplicate consumes none. No section work, disk, authority/socket lock or wait on these caller methods.

retain_current scans at most8 records in admission order, invokes predicate once each with scalar facts. For false, cancel_encode(originalID) BEFORE removing its routing record and increment count. Cancellation refusal retains that record; already cancelled prefix remains accepted and is not claimed rolled back. No drive/poll occurs before cancellation, so started charge persists until actual completion collection even if a reply already exists. True retains the original capture/request unchanged; numerical relevance does not certify a different capture token. This operation does not itself establish Wanted, observer/session lifecycle or live generation/revision truth; those are the next source caller's responsibility.

collect_ready first calls pool.drive even when no routing records remain, so cancelled real completions release charge. Then scan at most8 records and poll their exact IDs. Pending retains the whole record. Ready/Failed removes only that record and returns its original session/request/capture paired with the whole result. Verify Ready capture==original record capture; mismatch becomes Internal{invariant:"source chunk encode result"}, never successful bytes. Preserve each completed record's admission order within this pass; Pending gaps may be bypassed because this is completion transport, not source priority or wire selection. Return all actual errors as owned result entries, rather than dropping successes when another request fails. Consumer must handle failure before whole-publication admission; it cannot infer success from an empty vector.

Implement existing WorkerLifecycle: stop_new delegates then marks stopping; cancel delegates then clears routing records (started charge remains in real pool); wait delegates and retains all routing records/results for actual collect or retry. close first stop_new, delegates actual pool close, clears records/marks closed ONLY on successful joined close. Timeout or sticky join failure retains book records and the same actual pool/handles for close retry, with admission Closing. Actual pool close cancels remaining results before waiting: retained records are shutdown bookkeeping, not a promise that collect_ready can recover cancelled results; normal consumers wait/collect before close. Successful close is idempotent. Default Drop disconnects through existing pool and makes no joined/quiescence claim. No final tick or authority mutation occurs here.

Reject putting the pool inside a TickContext because it has an independent lifecycle and must survive caller deadlines. Reject replacing or silently deduplicating captures on the same numeric tuple because result correlation belongs to the original token. Reject clearing started charge when dropping routing records, or manufacturing completion on timeout. Reject folding source budgets/fairness/current-Wanted truth into this owner without the separately designed authority consumer. No automatic runtime flag or synchronous fallback is introduced.
