# Background store owner

Baseline: `5b5a7962b1aca724c11249f20baac00d3b2b9276`. The original branch now contains all 46 previously accepted commits; push and exact remote HEAD were verified on 2026-10-01. Existing store providers are real, but `StoreMailbox::drive_workers` executes codec and filesystem work synchronously while holding the mailbox, preventing a production tick from polling the same owner during I/O. This node fixes that ownership dependency before runtime composition.

## Controller design and readiness

One filesystem backend and world lease belong to one background OS thread. The authority retains submission, occupancy, scheduling and acknowledgment on its own thread. A bounded channel transfers immutable save requests; per-job one-slot response channels return only commit/error/reservation facts. There is no authority handle, backend mutex or filesystem operation on the tick thread. Two active save slots remain the existing maximum; the single backend serializes actual disk access. Existing inline construction remains available for deterministic non-Send dependency doubles and retains its current behavior.

The exact additive public operation is `StoreMailbox::<B>::try_new_background(limits: StoreLimits, backend: B) -> Result<Self, ServerError>` where `B: DiskBackend + Send + 'static`. Existing `try_new` and `AutosaveScheduler<B>` signatures stay unchanged. This constructor and its only consumer are implemented and accepted serially in this node; no independent consumer needs a separate contract landing. Real `DiskStore` already qualifies because its I/O hooks and factory are Send. Startup opens the disk owner and reads startup metadata before moving it into the worker; startup work is outside the tick.

Private representation: backend ownership is either inline or background. `Job` retains `Arc<SaveRequest>` plus ticket and current reservation vector on the authority thread. A dispatched slot retains this job and exactly one pending response receiver. The worker command receives a cloned Arc and small reservation vector, not a deep copy on the tick. The worker clones the backend request inside its thread, performs the existing chunk encode/shrink and checked backend-write algorithm, discards the backend's echoed snapshots, and drops its request Arc before publishing `(ticket, committed, error, reservations)`. The authority unwraps the remaining Arc only when forming the owned completion. Wrong backend tickets still produce Internal and adopt no durable revisions. Completion occupancy remains charged until poll. Cancellation only returns unstarted queue jobs; dispatched jobs and replies remain owned.

Channel capacity is `limits.workers()+1`, hence at most three queued commands. There are at most `limits.workers()` dispatched save commands/responses; one serialized lifecycle request may additionally exist. Existing four-job, per-family (including sixteen player snapshots), eight-chunk and 4 MiB admission ceilings remain the sole save occupancy limits. Each background owner has one codec and compression scratch; do not keep a second idle codec/scratch on the authority thread. Constructor validates zero workers and prepares codec before spawn; thread-spawn failure returns the typed I/O error without starting an owner. Constructor-created resource cleanup is RAII only; no source persistence acknowledgment is invented.

`dispatch`, `poll`, `poll_tick`, and background `drive_workers` use only `try_send`/`try_recv`; full channels leave the original queued or dispatched owner intact. A background `drive_workers` call hands off queued work and adopts all currently available results, then returns without waiting. Inline drive retains existing semantics. Results shrink charged encoded bytes exactly once before being stored as completions. No large save-body clone in submit, poll or acknowledgment bookkeeping: add a crate-private reserved-length admission helper in `StoreLimits`, checking vector length before changing occupancy, and release occupancy using a borrowed completion rather than cloning its snapshots. Existing public `try_admit` continues checking caller estimates unchanged.

`flush` and scheduler flush are off-tick and may wait: repeatedly dispatch, collect and apply completed ownership until no relevant job remains, checking both caller's monotonic Clock and the real `Deadline::instant()` before every new wait. Wait at most 1 ms between empty polls, bounded by remaining deadline. Scheduler's final metadata submission must wait for its actual ticket until deadline instead of assuming one drive call completes it. A timeout retains all tracked jobs and metadata ticket for retry. No busy loop and no replay of an already applied completion.

Sync and close share the same thread and bounded channel. The mailbox retains one lifecycle receiver and its kind across caller timeout; a retry of the same kind consumes that original outcome rather than issuing another backend call. A different kind while unresolved refuses InvalidState. The worker checks the absolute deadline before beginning a queued lifecycle call; an expired queued request performs no backend I/O. Once a call begins, its real backend result is retained even if the caller times out. Successful backend close releases the lease only after existing provider barriers and makes the worker exit after sending its result. Mailbox close consumes that success and joins the now-finished thread before becoming closed. Failed backend close leaves the thread/backend alive for a new same-owner retry. No cancellation of an in-progress durability barrier and no detached thread on successful close. Unexpected backend/codec panic is caught around the operation and reported as Internal with original request ownership retained; it must not unwind the owner thread or silently acknowledge revisions. If a channel unexpectedly disconnects, return Internal with the original save snapshots and retain the lifecycle failure; never manufacture a successful close.
