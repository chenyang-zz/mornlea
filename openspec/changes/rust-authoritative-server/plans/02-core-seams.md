# F2 S1 compile-ready seams

This is a required input to the controller-owned 1.2 contract landing, not a claim that these prospective Rust types already exist. The accepted F1 SHA controls concrete domain, protocol and codec imports. The controller translates only those imports, then commits this surface and a success/failure consumer double before any rule or adapter worker starts. A mismatch with an accepted F1 type is a contract revision and requalification, not a worker-local alias.

## Checked admission, time and error policy

`ServerLimits` has private fields and `try_new(max_players: u8, queued_commands: usize, session_outbox: usize, ready_chunk_results: usize, snapshot_chunks: usize, snapshot_bytes: usize) -> Result<Self, ServerError>`. `TickBudget` has private fields and `try_new(commands: usize, fluid_updates: usize, fluid_rescan_cells: usize, farmland_checks: usize, farmland_block_reads: usize) -> Result<Self, ServerError>`. Both expose same-named read-only getters. The controller freezes configured legal ceilings from current Go bounds and proposed Rust admission limits after proving that every supported replay fits; observed high-water is evidence, not itself a constructor maximum. Validation rejects zero capacity, values above those configured ceilings and arithmetic overflow before allocating; tick work fields may be zero and must not exceed their frozen legal ceilings. `advance_tick` checks the budget again before draining because internal tests and deserialization may bypass a constructor. `Capacity` includes `{resource, limit, observed}`; rejection never consumes a sequence, arrival index, resource, or tick.

S2 alone owns `HandshakeLimits::try_new(pending: u8, hello_timeout: Duration, login_timeout: Duration)`, with 16 pending, 5 s hello and 10 s login defaults from current Go behavior. Reservation occurs before `AdmittedLogin`; expiry releases the slot once, and Memory/TCP call the same reservation/admission code. S1 admits at most eight already validated active logins. A ninth active login and a seventeenth pending handshake are separate tests at their respective owners.

`Deadline` wraps a process-local `std::time::Instant`, constructed by `Deadline::at(Instant)` or `Deadline::after(now: Instant, timeout: Duration) -> Result<Self, ServerError>` using checked addition. `expired(now)` uses the injected monotonic clock; no Unix nanoseconds or wall-clock conversion is accepted. A zero/expired deadline can still report a completed flush but cannot start a blocking wait. `Timeout` reports shutdown phase and outstanding ticket count; it never reports `Durable` for pending work.

## Single tick owner and mutation transaction

`AuthorityState` privately owns `sessions`, `tick`, `world`, `actors`, `inventory`, human and companion inboxes, pending generation keys, save state and publication. The serial reducer alone creates one `TickContext<'_>` for one tick; it borrows a single `MutationTxn<'_>` and publication buffer. It calls these phase entrypoints in order: `apply_player_commands`, `apply_companion_actions`, `apply_acquired_chunks`, `advance_actors`, `reconcile_subscriptions`, `advance_hostiles`, `advance_passives`, `settle_gameplay`, `advance_block_updates`, `finish_world`, `sweep_supports`, `commit`, `publish_and_advance_clock`. The `reconcile_subscriptions` call and `SetViews` equivalent occur immediately after actor advancement, before hostile and passive work. `engine_step_phase_test.go` and a Rust observable phase-edge replay guard this order.

The controller exposes only these `TickContext` methods to rule modules: `read() -> AuthorityReadView<'_>` for immutable current-tick world/actor/inventory facts; `charge(kind: WorkKind, units: usize) -> Result<(), ServerError>` for bounded work; `stage(effect: RuleEffect) -> Result<(), ServerError>` for validated, ordered changes; `emit(event: RoutedEvent) -> Result<(), ServerError>` for owned publication; and `transaction() -> &mut MutationTxn<'_>` for the two atomic block/resource operations below. The accepted 1.2 declaration must define every `WorkKind` and `RuleEffect` variant required by the 1.1 inventory, with owned fields and no `&'static` fixture shortcuts. Providers never receive mutable `AuthorityState`, session queues, save handle or outbox. A rule rejection leaves `MutationTxn`, inventory and publication unchanged; a later phase sees staged effects in Go parity order. `commit` runs once and turns staged changes into one ordered world delta per accepted block mutation.

The accepted human `PlacementIntent` supplies look and selected slot, while `PlayerControl.actions().primary` supplies the held primary-action bit; authority decides whether that bit resolves to mining, combat or no action. Neither payload supplies a trusted target or chunk revision. `resolve_place(actor: ActorKey, intent: PlacementIntent, read: &AuthorityReadView) -> Result<ResolvedPlacement, RuleReject>` and `resolve_mine(actor: ActorKey, control: &PlayerControl, read: &AuthorityReadView) -> Result<Option<ResolvedMining>, RuleReject>` raycast current authoritative pose/look, select the current item/block and capture the current chunk generation/revision; `None` means primary released or a higher-priority non-mining action. Companion target proposals enter `resolve_companion_place(actor: CompanionKey, target: BlockPos, block: BlockId, read: &AuthorityReadView) -> Result<ResolvedPlacement, RuleReject>` or `resolve_companion_mine(actor: CompanionKey, target: BlockPos, read: &AuthorityReadView) -> Result<ResolvedMining, RuleReject>` for the same checks. `ResolvedPlacement` and `ResolvedMining` have private constructors available only to authority resolution; they hold actor, dimension, target, resource/block identity, source tick and observed chunk generation/revision. Companion actions carry a proposed target, but authority re-resolves reach, geometry and current revision into the same resolved types. `MutationTxn::try_place(resolved: ResolvedPlacement) -> Result<MutationOutcome, RuleReject>` and `try_mine(resolved: ResolvedMining) -> Result<MutationOutcome, RuleReject>` are the only block/resource commit seams. The real controller-owned implementation lands in serial node 1.6 after the 1.2 declarations; it rechecks the captured revision/generation, actor authority, collision/target, resource and permitted block at commit and stages resource debit/credit with world mutation atomically. Failed checks change neither side. World acquisition owns generation keys and geometry reads; the inventory provider supplies checked debit/credit through the accepted transaction port. Companion placement commits in `settle_gameplay` and never mints a human `CommandEnvelope`. The accepted declarations name `ActorKey::{Player(SessionKey),Companion(CompanionKey)}` and closed `RuleReject` cases; the controller maps them to F1 outcome/event types.

`replay(seed, input_schedule, expected_events, expected_state_hash)` and `expect_rejected(input, expected_class, unchanged_hash)` are controller-owned helper signatures. At 1.2 they run an independently asserted deterministic double for admission/contract tests; the real provider/tick reducer is integrated and required at 3.1. Provider nodes may use an isolated single-phase `TickContext` harness with accepted 1.2 interfaces; they cannot claim the full reducer has already landed. Helpers compare fixture digests and final state and fail zero case discovery. The 1.2 double proves private resolved-target construction and success/error type flow. Node 1.6 proves a valid placement with exactly one debit and block delta and stale revision, missing item, full budget and duplicate provenance negatives with unchanged world/inventory state; 3.1 repeats these through the real reducer.

## Sessionless companion ingress

`CompanionActionEnvelope` is owned S1 input, not `PlayIntent` or `CommandEnvelope`. It carries `{companion_id: CompanionKey, source_tick: u64, request_id: AgentRequestId, generation: u64, attempt: u32, snapshot_digest: [u8; 32], action: CompanionAction}`. `CompanionAction` is closed to `Move {move_x: i8, move_z: i8, jump: bool, yaw: f32}`, `MineHold {target: BlockPos}`, `MineRelease`, and `Place {target: BlockPos, block: BlockId}`; all coordinates, yaw and block IDs are validated before admission. `CompanionReceipt::QueuedForTick {tick, arrival_index}` means admission only. The bounded inbox accepts at most four pending actions per tick by the proposed Go parity limit; full admission returns `Capacity` and consumes no provenance or index. A `(companion_id, request_id, generation, attempt)` duplicate is rejected. At the tick boundary, recheck active companion, task generation, request/snapshot identity, world target/chunk revision, range, permission and resources. The first valid action per active companion wins in arrival order; invalid/late actions are counted and leave no world effect. Move/mining intent enters the pre-physics companion phase; placement commits later in `settle_gameplay` after subscription reconciliation. Agent text never becomes an action. An Agent plan candidate is first validated against its frozen and current snapshots by S4/S1, then its task runner may submit a typed action envelope; S4 never directly mutates the world.

## Persistence and shutdown

The controller-owned S3 declarations are `SaveRequest {key: SaveKey, revision: u64, encoded_bytes: Vec<u8>, urgency: SaveUrgency}`, `SaveTicket(NonZeroU64)`, `SavePoll::{Pending,Durable {revision},Failed {class}}`, `SaveBudget {chunks: usize, bytes: usize}`, `SaveScheduleReport {urgent, autosave, retry, dirty, in_flight, estimated_unsaved_bytes, backpressured}`, and `FlushReport {durable, failed, outstanding}`. `SaveKey` is a closed typed world/player/companion/hostile/passive/metadata key, mapped to accepted F1 storage codecs; the controller freezes every variant and schema at 1.2. `StoreHandle::poll_tick` is nonblocking and schedules due retry, urgent, then autosave work in that order. Autosave begins on the accepted configured tick cadence and remains active until dirty and in-flight work clear. Failed dispatch returns snapshots to dirty/retry ownership. Backpressure enters at the accepted unsaved-byte limit and exits only below its 90% hysteresis threshold. Retry uses saturating tick backoff and preserves original revision; chunk unload cannot discard dirty or in-flight work. Per-request size, total pending bytes, eight pending chunks and two I/O workers are checked before enqueue. Flush includes dirty, pending, retry and metadata work; world/actor saves and metadata must cross their F1 durability boundary before `Durable` or successful shutdown.

The first `shutdown(deadline)` changes Running to Closing, stops new admission, drains already accepted human/chat/chunk/companion input and executes **exactly one final unpublished tick**. It cancels new Agent/hostile work before the tick, freezes actor/world snapshots after the tick, detaches sessions, and then waits for worker completion and ordered companion/hostile/passive/world/metadata flush, sync and store close. `advance_tick` and new submission fail `InvalidState` once Closing. If deadline or I/O fails, keep frozen authority and the world lease; a later `shutdown` resumes the remaining flush/close phase without a second tick or duplicate publication. Only successful close releases the lease. `ShutdownReport` identifies final tick, completed phase, durable/failed/outstanding tickets and whether a retry remains possible. Tests pin accepted buffered command applied once, zero final publication, timeout/retry, failed sync/retry, no blank-world fallback and idempotent success against `packages/server/server/shutdown_test.go`.

## Dispatch barrier

The controller records the accepted code SHA and an interface table for each declaration above in `ledger.md`. All named rule, transport, store and Agent test modules must be registered and have a nonempty behavioral double at that SHA. A worker packet cites that SHA, imports only accepted declarations and its read-only oracle, and stops on any missing variant or signature; the controller revises this contract, dependent packets and tests serially before resuming. The ledger records capacity measurements, exact constructor bounds, fixture hashes, error precedence, test counts and scoped rollback.
