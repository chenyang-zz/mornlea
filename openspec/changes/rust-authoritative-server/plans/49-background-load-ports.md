## Actual provider design

Implement both load ports for StoreMailbox<B>. No new public provider constructor: try_new_background retains backend/codec/lease on the existing sole OS owner; inline try_new remains for non-Send doubles. Exact provider editable paths: store/background.rs, store/mailbox.rs, new private store/loads.rs, store/mod.rs (private declaration), tests/persistence_failure.rs registration, new tests/persistence_failure/loads.rs, store/AGENTS.md ownership note. Contract/world source read-only at accepted SHA. Scheduler, generation, state, bin, transport, Agent, Go, schemas and sealed corpus read-only. Root owns all OpenSpec and integration edits.

Private loads.rs stores two bounded ledgers: at most16 player requests and8 chunk requests, each count includes queued, started and unconsumed replies. Player tickets and chunk IDs mint independent monotonically increasing nonzero u64 counters, checked before admission; overflow returns Internal with invariant player load ticket space or chunk load ticket space. Zero chunk generation refuses before capacity/ticket mutation. Full player lane Capacity(PendingLogins,16,17), full chunk lane Capacity(ChunkResults,8,9); no backend work or counter change on refusal. Unknown or consumed polls Pending, unknown/repeated cancels Ok. A same-key new request is allowed and independently charged; consumers own supersession identity.

Each ledger record retains key/identity/generation/deadline, queued or one receiver state, and cancelled bit. At most two dispatched load replies in total, matching existing workers count (1 or2); independent existing save slots remain at most2. All command families share the existing workers()+1 bounded channel (max3), no second backend/scratch, Mutex, filesystem read or Ready construction on authority thread. Each load result uses a per-request one-slot channel. Tick drive/poll performs at most24 ledger observations and nonblocking try_send/try_recv; no unbounded history. Authority dispatch alternates save and load priority per drive turn, and load dispatch alternates player/chunk candidates, both FIFO within lane. Full channel keeps the exact queued record. Existing save occupancy/caps remain unchanged.

Extend private background command with player/key or chunk/key/generation/deadline and typed reply. Worker checks deadline before starting load, expired returns Timeout(Load) and no backend call. Then catch_unwind around backend.load plus validation/preparation, map panic Internal(store load panic), retain backend alive and return typed result. Match only LoadedValue::Player for requested player (UUID bytes must match requested ID; mismatch InvalidInput loaded_player); match only LoadedValue::Chunk for chunk, then PreparedChunk::try_new on that same owner. Wrong family Internal(store load family). Only ServerError::Io {operation: Load, kind: NotFound} becomes Loaded(None). Every other storage, future-version or I/O error is returned unchanged. Starting before expiry may finish afterward; its real outcome survives for poll, with no replay or timer-created absence.

Inline load dispatch records queued work; explicitly named drive_workers executes it, never start/poll. Background drive_workers collects load replies and dispatches alongside save work without waiting. load poll collects available replies and releases that ledger record on consumption; returned prepared chunks move, not deep clone. Cancellation of queued records releases immediately and does not run disk load; cancellation after dispatch retains record/receiver/capacity until owner replies, then collect discards exactly once and releases. No unbounded cancellation tombstones, no lost reply or resurrection.

The first Close attempt freezes new load admission, including across timeout/retry; later load starts refuse InvalidState(Closing), or Closed after successful close. Close with any retained load record refuses InvalidState(Closing) before backend/lifecycle close; caller must cancel or consume loads, and started cancellation remains retained until completion. Existing records can still drive/poll/cancel while admission is frozen. This prevents queued data from being stranded behind owner exit, including after a timed-out close. Existing save admission and sync semantics stay unchanged: sync retains FIFO barrier semantics for already-dispatched commands and makes no promise to drain undispatched queues. The future runtime stops load admission and drains/cancels owned jobs in WaitWorkers before StoreClose. Flush retains load records, dispatches/collects memory handoffs alongside saves and never claims their outcome consumed on behalf of login/acquisition. No deadline spin: existing off-tick wait bounds remain.
